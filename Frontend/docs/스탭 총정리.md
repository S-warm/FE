# FE 백엔드 통합 스텝 정리

작성일: 2026-05-10
대상 브랜치: `codex/fe-jihyun-latest`
목적: Step 1부터 현재 단계까지의 설계, 구현, 남은 작업을 한 문서에서 이어서 볼 수 있게 정리

## 0. 전체 요약

이 프로젝트의 프론트엔드 작업은 크게 4구간으로 나뉜다.

1. Step 1 ~ 10
- mock 중심 UI를 실제 API 구조로 옮길 수 있도록 기반을 설계한 단계

2. Step 11 ~ 15
- 페이지가 mock을 직접 보지 않도록 소비 구조를 query / service / adapter / view-model 기반으로 바꾼 단계

3. Step 16 ~ 20
- HTTP 클라이언트, 인증, 도메인 HTTP 서비스, 서버 에러 매핑, status polling까지 연결한 단계

4. Step 21 ~ 22
- 실 API raw 응답 기준 보정과 정책 확정이 남아 있는 마감 단계

현재 판정:
- Step 1 ~ 20: 대부분 완료
- Step 21: 부분 완료
- Step 22: 미완료

## 1. Step 1 ~ 10: 기반 구조 설계 단계

### Step 1. Mock 의존성 분리 준비

목표:
- 어떤 페이지가 어떤 mock에 직접 의존하는지 파악
- mock 직접 참조를 끊기 위한 중간 계층 필요 지점 정리

정리 결과:
- 페이지와 결과 탭, 일부 레이아웃이 mock shape를 직접 알고 있던 구조
- 이후 `types -> adapters -> services -> queries`가 중간 계층으로 필요하다는 방향이 확정됨

의미:
- 이 단계에서 이후 리팩토링의 범위와 우선순위가 잡혔다

### Step 2. 타입 경계 분리

목표:
- raw API 타입과 FE view-model 타입 분리

정리 결과:
- `src/types/api/**`
- `src/types/view-model/**`

현재 상태:
- 타입 분리 구조 완료
- 페이지는 최종적으로 view-model만 소비하는 방향으로 정리됨

### Step 3. 입력 / 폼 구조 선정리

목표:
- `SimulationSetupPage`의 입력값을 생성 API body로 안전하게 변환할 구조 만들기

정리 결과:
- `SimulationFormViewModel`
- `SimulationCreateRequestDto`
- `mapSimulationFormToCreateRequest(...)`

현재 상태:
- mapper 구현 완료
- 단, `endUrl`은 아직 request DTO에 포함되지 않는 FE-only 상태

### Step 4. 생성 폼 검증 설계

목표:
- 백엔드 DTO 검증 규칙을 프론트에 선반영

정리 결과:
- 클라이언트 validation 구조 설계
- 필드별 에러 메시지 정책 정리

현재 상태:
- `validateSimulationSetupForm(...)` 동작
- 이후 Step 19에서 서버 에러까지 필드에 환원하는 구조로 확장 완료

### Step 5. 결과 탭 공통 데이터 모델 확정

목표:
- 결과 탭들이 공통으로 쓰는 page / issue / severity / count 축 정리

정리 결과:
- 결과 탭 공통 view-model 기준이 생김
- header와 tab 데이터 경계가 분리됨

현재 상태:
- 결과 탭 전체가 공통 page summary 개념 위에서 동작

### Step 6. Adapter 계층 설계

목표:
- 페이지가 raw 응답을 직접 모르도록 adapter 계층 설계

정리 결과:
- overview / issues / ai-fix / heatmap / wcag adapter 구조 설계

현재 상태:
- `src/adapters/**` 구현 완료
- Step 21에서 실응답 기준 미세 조정만 남아 있음

### Step 7. Service 레이어 골격 설계

목표:
- fetch 없이도 mock 기반으로 먼저 서비스 구조를 완성

정리 결과:
- 도메인별 service interface 정리
- 공통 에러 객체 방향 정리

현재 상태:
- interface + mock 구현 + http 구현 구조 완료

### Step 8. React Query 도입 뼈대 설계

목표:
- service와 페이지 사이를 query hook으로 연결

정리 결과:
- query hook 목록
- query key 규칙
- provider 위치 정리

현재 상태:
- `QueryClientProvider` 연결 완료
- 각 페이지가 query hook으로 데이터 소비

### Step 9. 로딩 / 빈 상태 / 에러 상태 표준화

목표:
- API 붙기 전에 페이지 상태 UX를 공통 패턴으로 정리

정리 결과:
- `ErrorState`
- `EmptyState`
- `ResultPageSkeleton`
- `InlineError`

현재 상태:
- 주요 페이지에 공통 상태 패턴 반영 완료

### Step 10. 점진적 실장 계획

목표:
- 한 번에 다 바꾸지 않고 구조를 순서대로 교체

의미:
- 이후 Step 11 ~ 15가 이 계획에 따라 실제로 진행됨

## 4. Step 21 ~ 22: 마감 단계

### Step 21. WCAG / Heatmap 실응답 기준 보정

목표:
- 실 API raw JSON 기준으로 adapter 최종 보정

현재 상태:
- 부분 완료

이미 반영된 것:
- heatmap 좌표 `0~1`, `0~100` 정규화 방어

아직 남은 것:
- WCAG가 simulation-level인지 page-level인지 raw 확인 필요
- heatmap의 `currentAgeGroup`, `pagination`, `errorPoints` 구조 실응답 대조 필요

핵심 제한:
- 현재 워크스페이스에 실 raw JSON 캡처 파일이 없음

### Step 22. 정책 확정

목표:
- 실제 운영에서 의미가 달라질 수 있는 남은 항목 정리

남은 항목:
- persona device 6종 -> BE 3종 정책
- `endUrl` FE-only 유지 여부
- simulation status enum 전역 정책
- PDF 다운로드 / 공유 버튼 정책
- refresh token / 401 재시도 정책

현재 상태:
- 미완료

## 5. 현재 프론트 완성도 평가

| 영역 | 상태 | 평가 |
|---|---|---|
| 구조 설계 | 완료 | 매우 안정적 |
| 페이지 소비 구조 전환 | 완료 | mock 직접 참조 제거됨 |
| HTTP / 인증 / 서비스 연결 | 완료 | 실제 호출 골격 동작 |
| 서버 에러 매핑 | 완료 | 폼 UX 연결됨 |
| 상태 polling | 완료 | process 흐름 연결됨 |
| 실응답 기준 DTO / adapter 보정 | 일부 미완료 | raw 필요 |
| 정책 확정 | 미완료 | 협의 필요 |

종합 판정:
- 프론트는 현재 `백엔드 통합 직전 단계`라고 볼 수 있다.
- 다만 `통합 시작 가능`과 `통합 완료 판정 가능`은 다르다.
- 지금은 전자에는 도달했고, 후자는 Step 21 ~ 22가 마무리되어야 한다.

## 8. 최종 결론

Step 1부터 지금까지의 흐름은 아래처럼 정리할 수 있다.

- Step 1 ~ 10: 구조를 설계했다
- Step 11 ~ 15: 페이지를 새 구조로 옮겼다
- Step 16 ~ 20: 실제 백엔드 연결 골격을 붙였다
- Step 21 ~ 22: 실응답 검증과 정책 마감을 남겨두고 있다

즉, 지금 프론트는 `설계 단계`는 이미 지난 상태고, `실연결 직전 단계`에 와 있다.
다음부터 중요한 건 구조를 다시 바꾸는 것이 아니라, 실제 응답과 정책을 현재 구조에 안전하게 맞춰 넣는 일이다.
